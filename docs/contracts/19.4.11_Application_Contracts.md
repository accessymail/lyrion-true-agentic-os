# LYRION 19.4.11 — Application Boundary Contracts

## Status

ARCHITECTURE APPROVED — CONTRACT DESIGN IN PROGRESS

## Contract Principles

- Application contracts do not grant authority.
- Frontend data is untrusted.
- Model/provider output is untrusted.
- Voice identity is not authorization.
- Every request is bound to an authenticated principal and application session.
- Privileged operations remain behind Capability Gateway / Aegis and Secure Executor.
- Existing domain contracts SHALL be reused where applicable.
- Cross-session and cross-principal references MUST fail closed.
- Realtime events MUST be bounded, correlated, validated, and replay-resistant.

## Contract Domains

1. Application Session
2. Voice Turn
3. Realtime Events
4. Correlation Context
5. Authentication Context
6. Errors
7. Resource Limits
8. Reconnect / Resume
9. Cancellation / Interruption
10. Application Runtime Interface

## Contract Design Rule

Contracts MUST be finalized before implementation.
Every contract MUST define identity, lifecycle, validation, ownership, failure semantics, and security constraints.

## 3. Existing Domain Contract Mapping

19.4.11 SHALL wrap and compose existing domain contracts rather than duplicate them.

### 3.1 Existing Voice Contracts

The application boundary SHALL reuse the existing Voice Session, Voice Turn, Voice Streaming, and Voice Authentication contracts.

The application layer MUST NOT create a competing VoiceSession or VoiceTurn representation.

### 3.2 Existing Cognitive Contracts

The application boundary SHALL reuse existing cognitive request/result contracts.

Cognitive output remains untrusted data and MUST NOT become application authorization.

### 3.3 Existing PIAE Contracts

Existing DecisionResult, DecisionContext, Opportunity, DecisionConstraints, correlation_id, and idempotency semantics SHALL be reused.

The application MUST preserve decision identity and correlation when bridging into RPII/PIAE.

### 3.4 Existing RPII Contracts

Existing RPIIContext and RPIICycleResult SHALL remain the authoritative RPII lifecycle contracts.

The application boundary SHALL bind application session and voice interaction identity to the existing RPII session_id and interaction_id fields.

### 3.5 Existing Capability Contracts

CapabilityRequest remains the immutable request for authority.

The application MUST NOT construct a self-authorized CapabilityRequest.

CapabilityRequest principal_id MUST come from an explicitly validated application principal binding.

CapabilityRequest decision_id, task_id, correlation_id, and idempotency_key MUST preserve the originating decision/task/request lineage.

### 3.6 Existing Authorization Contracts

AuthorizationResult remains the authoritative result of Aegis authorization.

The application MUST NOT interpret frontend/session state as equivalent to AuthorizationResult.granted.

Authorization failures MUST remain failures and MUST NOT be transformed into successful application state.

### 3.7 Existing Execution Contracts

ExecutionRequest, ExecutionPlan, ExecutionResult, and ExecutionAdmission SHALL remain the authoritative execution contracts.

The application MUST NOT directly construct privileged execution authority outside Capability Gateway / Aegis.

Execution identity MUST remain linked to the originating request_id and principal_id.

### 3.8 Existing Persistence Contracts

Voice session continuity SHALL reuse existing session revision and turn-sequence semantics.

Application idempotency SHALL use the existing durable IdempotencyStore where cross-request or cross-restart semantics are required.

The process-local Aegis ReplayGuard SHALL NOT be treated as the complete application replay-protection mechanism.

### 3.9 Application-Owned Contracts

The following concepts are newly owned by the application boundary:

- ApplicationPrincipalContext
- ApplicationSessionContext
- ApplicationCorrelationContext
- ApplicationTurnContext
- RealtimeClientEvent
- RealtimeServerEvent
- RealtimeEventEnvelope
- ApplicationError
- ApplicationResourceLimits
- SessionResumeRequest
- SessionResumeResult
- TurnCancellationRequest
- TurnCancellationResult
- ApplicationRuntime protocol

These contracts MUST reference existing domain identities rather than replacing them.

## 4. Identity and Lineage Contract

Every application operation MUST preserve the following lineage where applicable:

```text
authenticated principal
        ↓
application session
        ↓
voice session
        ↓
interaction / turn
        ↓
cognitive request/result
        ↓
decision_id / task_id
        ↓
capability request
        ↓
authorization result
        ↓
execution request/result
```

The application MUST NOT silently replace one identity with another.

The application MUST reject lineage mismatches.

The application MUST NOT derive authorization from lineage alone; authorization remains an explicit Aegis decision.

## 5. Application-Owned Contract Schemas

The following contracts are owned by the application boundary. They define transport, session, lifecycle, correlation, validation, and failure semantics. They MUST NOT grant authority.

### 5.1 ApplicationPrincipalContext

Purpose: represent the authenticated application principal after successful authentication.

Required fields:

- principal_id: stable validated principal identifier
- authentication_method: normalized authentication mechanism identifier
- authenticated_at: timezone-aware authentication timestamp
- expires_at: timezone-aware optional expiry timestamp

Constraints:

- principal_id MUST NOT be client-selected for privileged operations
- authentication state MUST be established server-side
- expired authentication MUST fail closed
- authentication_method MUST NOT itself imply authorization

### 5.2 ApplicationSessionContext

Purpose: bind one authenticated principal to one application session.

Required fields:

- application_session_id: unique application session identifier
- principal_id: authenticated principal identifier
- created_at: timezone-aware creation timestamp
- last_activity_at: timezone-aware activity timestamp
- expires_at: timezone-aware session expiry timestamp
- session_revision: monotonic revision counter
- status: explicit session lifecycle status

Constraints:

- principal_id MUST come from the validated authentication context
- session identifiers MUST be server-generated or cryptographically unpredictable
- cross-principal session access MUST fail closed
- expired sessions MUST reject new work
- session_revision MUST support optimistic concurrency where required

### 5.3 ApplicationCorrelationContext

Purpose: carry request lineage across application boundaries.

Required fields:

- correlation_id
- principal_id
- application_session_id
- voice_session_id when applicable
- interaction_id when applicable
- turn_id when applicable
- request_id when applicable

Constraints:

- correlation identifiers MUST be validated before use
- identifiers from unrelated sessions MUST be rejected
- correlation metadata MUST NOT be interpreted as authorization

### 5.4 ApplicationTurnContext

Purpose: bind one conversational turn to its application and Voice lifecycle.

Required fields:

- turn_id
- application_session_id
- voice_session_id
- interaction_id
- turn_sequence
- state
- correlation_id
- started_at
- completed_at when terminal

Constraints:

- turn_sequence MUST follow existing Voice Session ordering semantics
- turn state MUST permit only defined lifecycle transitions
- terminal turns MUST reject further mutable operations except explicitly defined recovery/inspection flows
- turn context MUST NOT grant execution authority

### 5.5 RealtimeEventEnvelope

Purpose: common envelope for every application realtime event.

Required fields:

- protocol_version
- event_id
- event_type
- correlation_id
- application_session_id
- sequence_number when ordering applies
- occurred_at
- payload

Constraints:

- event_id MUST be unique within the applicable replay window
- payload MUST be schema validated according to event_type
- payload size MUST be bounded before parsing or processing
- occurred_at MUST be timezone-aware
- unknown event_type MUST fail safely

### 5.6 RealtimeClientEvent

Purpose: represent a validated browser-to-server application event.

Supported initial event types:

- session_init
- audio_start
- audio_chunk
- audio_end
- text_input
- interrupt
- cancel
- ping
- resume

Client events MUST remain requests for application behavior rather than authority grants.

### 5.7 RealtimeServerEvent

Purpose: represent a validated server-to-browser event.

Supported initial event types:

- session_ack
- turn_started
- transcript_delta
- cognitive_state
- response_delta
- audio_start
- audio_chunk
- audio_end
- interrupted
- cancelled
- error
- degraded
- recovery
- session_resumed

Server events MUST NOT expose secrets, internal authorization data, internal stack traces, or sensitive infrastructure details.

### 5.8 ApplicationError

Purpose: stable client-safe error representation.

Required fields:

- code
- message
- correlation_id
- retryable
- occurred_at

Constraints:

- error codes MUST be stable and bounded
- message content MUST be safe for external disclosure
- sensitive implementation details MUST remain internal

### 5.9 ApplicationResourceLimits

Purpose: explicit limits for externally influenced application resource consumption.

Required categories:

- maximum concurrent application sessions
- maximum active turns per session
- maximum realtime event bytes
- maximum audio chunk bytes
- maximum queued audio bytes
- maximum concurrent cognitive operations
- maximum concurrent provider operations
- maximum reconnect attempts
- maximum resume attempts
- maximum turn duration
- maximum session idle duration

Limits MUST be finite, validated, and enforced before unbounded allocation.

### 5.10 SessionResumeRequest

Purpose: request continuation of an existing application/Voice session.

Required fields:

- application_session_id
- voice_session_id when applicable
- last_known_session_revision
- last_known_turn_sequence
- correlation_id

Constraints:

- the requester MUST already authenticate as the owning principal
- stale or invalid session state MUST fail closed
- resume MUST NOT automatically repeat privileged execution

### 5.11 SessionResumeResult

Purpose: return the validated resumability state.

Required fields:

- application_session_id
- voice_session_id when applicable
- resumed: boolean
- current_session_revision
- next_turn_sequence
- reason when resume is rejected or degraded

### 5.12 TurnCancellationRequest

Purpose: request cancellation/interruption of one active application turn.

Required fields:

- turn_id
- application_session_id
- voice_session_id
- correlation_id
- reason

Constraints:

- cancellation MUST be scoped to the authenticated owning session
- cancellation MUST be idempotent
- cancellation MUST invalidate late output for the cancelled turn
- cancellation MUST NOT revoke or alter Aegis authorization semantics

### 5.13 TurnCancellationResult

Purpose: report cancellation disposition.

Required fields:

- turn_id
- cancelled: boolean
- state
- correlation_id
- occurred_at

### 5.14 ApplicationRuntime Protocol

The application runtime contract SHALL expose orchestration operations only.

Conceptual operations:

- create_session
- get_session
- begin_turn
- submit_text
- submit_audio
- interrupt_turn
- cancel_turn
- resume_session
- close_session

The application runtime MUST delegate privileged work to the existing RPII/PIAE → Capability Gateway/Aegis → Secure Executor path.

It MUST NOT expose a direct privileged execution operation to frontend clients.

## 6. Contract Validation Rules

All application contracts MUST enforce:

- timezone-aware timestamps
- bounded strings and payloads
- immutable security-sensitive state where practical
- explicit lifecycle values
- cross-field consistency
- session/principal ownership
- correlation lineage
- replay/idempotency requirements
- fail-closed behavior on invalid state

Application contracts MUST reject malformed or inconsistent data before invoking domain services.

## 7. Contract Authority Boundary

## 8. Wire-Level Interface Contract

This section freezes the externally visible application transport semantics without selecting a concrete authentication provider implementation.

### 8.1 Secure Application API over HTTPS

The application control plane SHALL use HTTPS/TLS in production.

Initial resource families:

- session creation
- session inspection
- session resume
- turn submission
- turn cancellation
- health/readiness
- bounded application configuration/state operations where explicitly approved

The exact endpoint paths, HTTP methods, request schemas, response schemas, status codes, authentication mechanism, and rate limits SHALL be finalized before implementation.

The HTTPS API MUST:

- require an authenticated application principal where the operation is not explicitly public;
- derive principal identity from trusted authentication state;
- bind requests to the owning application session;
- validate payloads before invoking domain services;
- enforce request-size and resource limits before unbounded allocation;
- reject expired, malformed, cross-session, cross-principal, and invalid-correlation requests;
- return stable client-safe ApplicationError values;
- never expose secrets, stack traces, internal authorization details, or sensitive infrastructure data;
- never expose a direct privileged execution endpoint.

### 8.2 Secure Realtime Control over WSS

The realtime application/control plane SHALL use WSS in production.

The initial realtime endpoint SHALL represent one authenticated application realtime connection bound to one application session.

Client events SHALL use RealtimeEventEnvelope and RealtimeClientEvent semantics.

Server events SHALL use RealtimeEventEnvelope and RealtimeServerEvent semantics.

Realtime processing MUST enforce:

- authenticated session binding;
- event schema validation;
- bounded event and payload size;
- event identity uniqueness within the replay window;
- ordering where sequence_number applies;
- rejection of malformed, unknown, stale, duplicated, or cross-session events;
- bounded connection lifetime and resource consumption;
- explicit interruption/cancellation semantics;
- safe reconnect/resume behavior;
- no automatic repetition of privileged execution after reconnect or resume.

WSS MUST NOT provide a privileged execution operation.

### 8.3 WebRTC Voice/Media Plane

WebRTC SHALL be the preferred browser media transport for realtime voice.

The WebRTC media plane SHALL carry only media/session material necessary for the authorized voice interaction.

Browser microphone access, media permission state, and WebRTC connection state MUST NOT be interpreted as application authorization.

WebRTC signaling and session establishment MUST remain subject to the authenticated application session and correlation model.

WebRTC MUST NOT bypass the Application Runtime, Capability Gateway/Aegis, or Secure Executor boundaries.

Late, stale, cancelled, or superseded voice output MUST NOT be delivered to an invalidated turn.

### 8.4 Transport-to-Runtime Binding

HTTPS, WSS, and WebRTC SHALL converge on the same Application Runtime boundary.

The canonical path is:

Frontend/HUD-FUI
→ HTTPS/WSS/WebRTC transport boundary
→ authenticated application session
→ Application Runtime
→ Voice/Cognitive Runtime
→ RPII/PIAE
→ Capability Gateway/Aegis
→ Secure Executor
→ verification/state feedback
→ application response transport

No transport may manufacture authorization, elevate privilege, or introduce an alternate execution path.

### 8.5 Authentication Provider Independence

The application contract defines the requirement for an authenticated principal but does not prescribe a specific authentication provider at this stage.

Concrete authentication selection SHALL be a separate implementation decision and MUST preserve:

- stable principal identity;
- authenticated-at and expiry semantics;
- server-side verification;
- session ownership;
- revocation/expiry handling;
- fail-closed behavior.

The frontend MUST NOT be trusted as the source of principal identity or authorization state.

### 8.6 Implementation Freeze Rule

No application endpoint, WebSocket handler, or WebRTC signaling implementation SHALL be considered contract-complete until its request/response or event schema maps to an approved application contract and its security/lineage behavior is defined.

## 9. Final Wire Contract Matrix

This section closes the remaining wire-level contract gaps before implementation.

### 9.1 HTTPS Resource Model

The initial secure application API SHALL expose only resources required for the 19.4.11 application boundary.

| Resource | Method | Authentication | Purpose |
| --- | --- | --- | --- |
| `/v1/sessions` | POST | authenticated application principal | create application session |
| `/v1/sessions/{session_id}` | GET | owning principal | inspect current session state |
| `/v1/sessions/{session_id}/resume` | POST | owning principal | request session/Voice continuity resume |
| `/v1/turns` | POST | authenticated application principal | submit one bounded application turn |
| `/v1/turns/{turn_id}/cancel` | POST | owning principal | cancel one active turn |
| `/v1/health` | GET | public or deployment-restricted | liveness |
| `/v1/ready` | GET | public or deployment-restricted | readiness |

These routes are application-boundary operations only.

No route SHALL expose direct capability authorization, execution admission creation, SecureExecutor invocation, shell access, filesystem authority, or arbitrary tool execution.

### 9.2 HTTPS Request Rules

Every authenticated request MUST resolve its principal from server-validated authentication state.

Client-controlled `principal_id` MUST NOT establish identity.

Session identifiers, correlation identifiers, turn identifiers, and request identifiers MUST be validated for ownership and lifecycle state.

Requests MUST have finite body-size limits.

JSON payloads MUST be schema validated before domain invocation.

The application MUST reject expired sessions, cross-principal access, cross-session correlation, malformed state, unsupported content types, and invalid lifecycle transitions.

### 9.3 HTTP Status Contract

The application SHALL use stable transport status semantics:

- `200 OK` — successful read or completed operation.
- `201 Created` — newly created session/resource.
- `202 Accepted` — bounded asynchronous work accepted but not yet terminal.
- `204 No Content` — successful operation with no response body where appropriate.
- `400 Bad Request` — malformed or semantically invalid application request.
- `401 Unauthorized` — authentication missing or invalid.
- `403 Forbidden` — authenticated principal lacks permission for the requested application operation.
- `404 Not Found` — resource does not exist or is intentionally indistinguishable for security reasons.
- `409 Conflict` — lifecycle, revision, sequencing, or idempotency conflict.
- `413 Content Too Large` — request exceeds configured size limits.
- `415 Unsupported Media Type` — unsupported content type.
- `422 Unprocessable Content` — syntactically valid request failing application validation where distinct from malformed input.
- `429 Too Many Requests` — rate/resource limit exceeded.
- `500 Internal Server Error` — unexpected internal failure without sensitive detail disclosure.
- `503 Service Unavailable` — dependency/runtime not currently ready to serve the operation.

Client-visible failures MUST use ApplicationError semantics.

### 9.4 Authentication Binding

The application layer SHALL remain authentication-provider independent.

Authentication MUST establish:

- authenticated principal identity;
- authentication method;
- authenticated-at timestamp;
- expiration/revocation state;
- server-side validation result.

The concrete mechanism MAY be session-cookie based, bearer-token based, mTLS-backed, OIDC/OAuth-backed, or another approved mechanism in a future implementation decision.

No mechanism is authorized merely because it exists; the selected mechanism MUST preserve the application security invariants.

For browser sessions, credential transport MUST use secure transport and SHOULD use secure, HttpOnly, appropriately scoped cookies when cookies are selected.

### 9.5 Browser Origin and CSRF Contract

The browser application SHALL use an explicit allowlist of trusted origins.

Wildcard credentialed origins MUST NOT be used.

Cross-origin requests MUST be rejected unless the origin is explicitly permitted by deployment configuration.

When browser credentials use cookies, state-changing HTTPS operations MUST implement an appropriate CSRF defense.

WSS and WebRTC signaling MUST validate the browser origin where the deployment model exposes an origin-bearing browser connection.

Origin validation MUST NOT replace authentication or authorization.

### 9.6 WSS Wire Contract

One WSS connection SHALL bind to one authenticated application session.

Each realtime event SHALL carry:

- protocol version;
- event identifier;
- event type;
- correlation identifier;
- application session identifier;
- sequence number where ordering applies;
- timezone-aware event timestamp;
- bounded validated payload.

The server MUST reject:

- malformed events;
- unknown event types;
- oversized events;
- invalid session binding;
- cross-session identifiers;
- stale sequence values;
- replayed event identifiers within the active replay window;
- unsupported protocol versions.

The server SHALL define a bounded heartbeat/idle timeout and SHALL close connections that exceed configured resource or lifecycle limits.

### 9.7 WSS Ordering and Replay

Realtime sequencing protects transport/application events.

Capability/execution idempotency remains a separate security domain.

WSS event replay protection MUST NOT be treated as a substitute for durable privileged-operation idempotency.

Reconnect MUST establish a new validated transport binding.

Resume MUST reconstruct only valid application/Voice state and MUST NOT repeat a previously admitted privileged execution.

### 9.8 WebRTC Signaling Boundary

WebRTC SHALL be used for browser realtime media.

WebRTC signaling SHALL occur through the authenticated application boundary.

The signaling exchange MUST bind to the owning application session, voice session, turn lifecycle, and correlation context.

ICE/SDP/media connection state MUST NOT independently establish application authority.

WebRTC media MUST NOT directly invoke privileged domain services.

### 9.9 Audio Limits

Inbound and outbound audio handling MUST enforce finite limits for:

- maximum individual chunk size;
- maximum queued audio bytes;
- maximum active audio duration;
- maximum simultaneous media sessions;
- maximum per-session buffering;
- maximum realtime message rate.

Limits MUST be enforced before unbounded buffering or expensive processing.

### 9.10 Idempotency

Every operation capable of causing externally observable state mutation SHALL define idempotency semantics.

Repeated application requests with the same validated idempotency identity MUST NOT unintentionally create duplicate sessions, turns, cancellations, or resumptions.

Privileged capability/execution idempotency remains governed by the existing capability/execution contracts and persistence mechanisms.

Application-level idempotency MUST NOT manufacture authorization.

### 9.11 Reconnect and Recovery

Reconnect SHALL NOT imply automatic replay of client commands.

The client MUST provide bounded resume state.

The server SHALL validate:

- authenticated principal ownership;
- application session identity;
- voice session identity;
- session revision;
- last-known turn sequence;
- resume eligibility.

Conflicting or stale state MUST fail closed.

Recovery MAY restore informational/conversational state but MUST NOT silently repeat privileged execution.

### 9.12 Security Headers and Browser Policy

Production HTTPS responses SHOULD include an explicit security-header policy appropriate to the deployment, including:

- HSTS;
- Content-Security-Policy;
- frame-ancestors or equivalent clickjacking protection;
- Referrer-Policy;
- X-Content-Type-Options.

Permissions Policy SHALL explicitly restrict unnecessary browser capabilities.

Client-visible diagnostics MUST remain bounded and sanitized.

### 9.13 Rate Limiting and Resource Governance

The application boundary SHALL enforce bounded limits for:

- authentication attempts;
- session creation;
- turn submissions;
- WSS event rate;
- audio throughput;
- reconnect frequency;
- resume attempts;
- concurrent sessions;
- concurrent active turns.

Rate/resource exhaustion MUST fail safely and MUST NOT bypass authorization or queue unbounded work.

### 9.14 Production TLS Boundary

Production HTTPS and WSS traffic MUST use TLS.

TLS termination MAY occur at a trusted reverse proxy, load balancer, ingress, or application server.

When TLS terminates before the application process, the deployment MUST securely propagate authenticated transport metadata and MUST prevent spoofing of forwarded security headers.

Direct plaintext external exposure MUST NOT be used for production application traffic.

Local development MAY use loopback HTTP where explicitly configured, but development behavior MUST NOT weaken production security contracts.

### 9.15 Observability Contract

Every externally initiated operation SHOULD preserve a stable correlation identifier across:

transport → application session → voice turn → cognition → RPII/PIAE → capability request → execution → result.

Security and audit logs MUST record security-relevant lifecycle events without exposing secrets, raw credentials, unnecessary sensitive audio, or unrestricted model/provider output.

Client-visible errors MUST remain decoupled from internal stack traces and security diagnostics.

### 9.16 Final Implementation Rule

A 19.4.11 implementation is contract-complete only when each externally reachable operation has an approved definition for:

- authentication;
- authorization boundary;
- request/event schema;
- response/event schema;
- lifecycle behavior;
- validation;
- limits;
- timeout;
- replay/idempotency;
- correlation;
- error semantics;
- observability;
- degraded/recovery behavior.

No implementation SHALL introduce a transport-specific authority model.

### 9.17 WebRTC Signaling Wire Contract

WebRTC signaling SHALL use the authenticated application boundary.

The signaling exchange SHALL support only the minimum data required to establish the negotiated media connection.

Initial signaling message types:

- `webrtc_offer`
- `webrtc_answer`
- `webrtc_ice_candidate`
- `webrtc_end`

Each signaling message MUST include:

- protocol_version;
- event_id;
- application_session_id;
- voice_session_id;
- correlation_id;
- bounded signaling payload.

Signaling messages MUST be validated against the owning authenticated session.

Client-supplied SDP/ICE material MUST be size-bounded and schema-validated before processing.

WebRTC signaling MUST NOT carry:

- CapabilityRequest;
- AuthorizationResult;
- ExecutionRequest;
- ExecutionAdmission;
- credentials;
- secrets;
- arbitrary tool instructions.

WebRTC media establishment MUST NOT imply authorization.

Failed or expired application sessions MUST terminate or reject associated signaling operations.

## 10. Concrete Wire DTO Contracts

This section defines the application-facing wire DTO shape without selecting a concrete authentication provider.

### 10.1 Session Creation

Request:

- optional client correlation_id;
- no client-supplied principal_id;
- no client-supplied authorization fields.

Response:

- application_session_id;
- principal context summary safe for the authenticated client;
- created_at;
- expires_at;
- session_revision;
- status;
- correlation_id.

The server SHALL generate the application_session_id and establish principal ownership from trusted authentication state.

### 10.2 Session Inspection

Request path:

- application_session_id.

Response:

- application_session_id;
- owning principal context summary;
- session status;
- session_revision;
- last_activity_at;
- expires_at;
- active turn summary where disclosure is approved;
- correlation_id.

The response MUST NOT expose secrets, credentials, internal policy state, capability grants, execution internals, or raw infrastructure state.

### 10.3 Session Resume

Request:

- application_session_id;
- voice_session_id when applicable;
- last_known_session_revision;
- last_known_turn_sequence;
- correlation_id;
- idempotency identity.

Response:

- application_session_id;
- voice_session_id when applicable;
- resumed;
- current_session_revision;
- next_turn_sequence;
- reason;
- correlation_id.

Resume MUST be idempotent and MUST NOT repeat privileged execution.

### 10.4 Turn Submission

Request:

- application_session_id;
- voice_session_id when applicable;
- client turn correlation;
- bounded text input or a reference to an accepted realtime audio turn;
- idempotency identity.

The client MUST NOT submit:

- principal_id as an authority claim;
- CapabilityRequest;
- AuthorizationResult;
- ExecutionRequest;
- ExecutionAdmission;
- execution authority;
- arbitrary tool invocation directives.

Response:

- turn_id;
- application_session_id;
- voice_session_id when applicable;
- turn_sequence;
- lifecycle state;
- correlation_id;
- accepted_at;
- bounded result/status metadata where available.

### 10.5 Turn Cancellation

Request:

- turn_id;
- application_session_id;
- voice_session_id;
- correlation_id;
- reason;
- idempotency identity.

Response:

- turn_id;
- cancelled;
- current state;
- correlation_id;
- occurred_at.

Cancellation MUST be idempotent and MUST invalidate late output for the cancelled or superseded turn.

### 10.8 Realtime Binary Framing

Audio binary data SHALL be accepted only where the negotiated realtime protocol explicitly permits it.

Every binary audio frame MUST remain bound to:

- authenticated connection;
- application session;
- voice session;
- active turn;
- input sequence.

Binary payload size MUST be bounded before processing.

Unbound binary data MUST be rejected.

### 10.9 Correlation Rules

Every externally initiated application operation MUST have one server-tracked correlation_id.

The server MAY accept a client-provided correlation identifier only after validating format, ownership scope, size, and protocol rules.

The server SHALL generate internal identifiers that are absent from the client request.

The following identifiers MUST NOT be conflated:

- correlation_id;
- application_session_id;
- voice_session_id;
- interaction_id;
- turn_id;
- request_id;
- execution_id;
- idempotency identity.

### 10.10 Error DTO Stability

ApplicationError SHALL remain the only generic client-visible application error envelope.

Error messages MUST be bounded and safe for disclosure.

Internal provider, database, network, authorization, execution, and stack-trace details MUST remain server-side.

### 10.11 Wire Contract Finalization

The DTOs in this section are the normative application-boundary shape for 19.4.11.

Implementation MAY use framework-specific internal models, but external serialization MUST preserve:

- field meaning;
- ownership;
- lifecycle semantics;
- validation;
- correlation;
- security boundaries;
- error semantics;
- size limits;
- idempotency behavior.

Any implementation deviation requires an explicit contract update before release.

## 11. Authentication Adapter Contract

The application boundary SHALL consume authentication through a provider-independent authentication adapter.

### 11.1 Adapter Responsibility

The authentication adapter SHALL:

- receive authentication evidence from the configured transport/application boundary;
- validate the evidence using the configured authentication mechanism;
- establish the authenticated principal or fail closed;
- return the normalized ApplicationPrincipalContext;
- enforce authentication expiry/revocation semantics;
- never grant application capability authority directly.

### 11.2 Adapter Result

A successful authentication result SHALL establish:

- principal_id;
- authentication_method;
- authenticated_at;
- expires_at when applicable.

A failed or expired authentication result MUST NOT establish an authenticated application principal.

### 11.3 Provider Independence

The adapter MAY be backed by:

- secure application sessions;
- bearer-token validation;
- OIDC/OAuth;
- mTLS;
- another explicitly approved authentication mechanism.

The provider is an implementation/configuration concern.

The Application Runtime MUST depend only on the normalized authentication adapter contract and ApplicationPrincipalContext.

### 11.4 Principal Binding

The application MUST derive principal_id from the validated adapter result.

The frontend MUST NOT establish or override principal identity.

Voice authentication evidence MAY contribute authentication evidence only through the existing Voice Authentication boundary and MUST NOT bypass the application authentication contract.

### 11.5 Authorization Separation

Authentication establishes identity.

Authorization remains the responsibility of the existing Aegis authorization boundary.

Authentication success MUST NOT be interpreted as capability authorization or execution permission.

### 11.6 Failure Semantics

Authentication failure, expiry, revocation, malformed credentials, unsupported credentials, and unverifiable authentication state MUST fail closed.

Client-visible errors MUST use bounded ApplicationError semantics and MUST NOT disclose credential-validation internals.

Application contracts are descriptive and transport-facing.

They MUST NOT contain fields that independently grant, elevate, or manufacture privileged authority.

Authorization MUST continue to be represented by the existing Aegis AuthorizationResult and execution admission contracts.

Execution MUST continue through existing ExecutionRequest / ExecutionAdmission / SecureExecutor semantics.
