# LYRION 19.4.11 — Proactive Voice Runtime + Complete Application Boundary
## Architecture Freeze

**Status:** APPROVED ARCHITECTURAL MILESTONE — IMPLEMENTATION NOT YET COMPLETE
**Milestone:** 19.4.11

## 1. Architectural Objective

19.4.11 establishes the first complete application boundary for LYRION.

The target experience is:

Frontend/HUD-FUI → Secure Application Boundary (HTTPS/TLS + WSS/WebRTC) → Authenticated Session → Voice Input/Turn → Cognitive Runtime → RPII/PIAE → Capability Request → Capability Gateway/Aegis → Execution Admission → Secure Executor → Verification → Audit/State Feedback → Cognitive Result → Voice Output Streaming → Frontend

The application layer MUST compose existing domain capabilities rather than duplicate them.

## 2. Core Security Invariant

LYRION MUST preserve:

Observation ≠ Opportunity ≠ Decision ≠ Authorization ≠ Execution

- Cognition does not grant authority.
- Voice identity is not authorization.
- Frontend state never grants authority.
- Model/provider output is untrusted.
- Model output cannot directly create privileged execution authority.
- RPII/PIAE does not directly perform privileged execution.
- Capability requests request authority; they do not grant authority.
- Capability Gateway / Aegis remains the authorization boundary.
- Secure Executor remains the execution boundary.
- No alternate privileged execution path may be introduced.

## 4. Trust Boundaries

### TB-1 Browser → Application

Browser-originated input is untrusted.

Validate:

- authentication/session binding
- Origin
- message schema
- message size
- sequence/correlation
- replay state
- authorization context
- rate/resource limits

Never trust frontend-maintained authority state.

### TB-2 Realtime Transport → Runtime

LYRION SHALL use a hybrid secure transport architecture:

- **HTTPS/TLS** — secure application/control plane for authentication, session lifecycle, ordinary application API operations, recovery, and non-realtime control.
- **WSS** — secure realtime application/control channel for correlated turn events, interruption, cancellation, recovery, and application state.
- **WebRTC** — preferred browser realtime media transport for microphone input and streamed voice output.

WSS and WebRTC MUST terminate at the Application Runtime boundary and MUST NOT create an alternate privileged execution path.

Realtime messages MUST be authenticated, session-bound, size-bounded, schema-validated, ordered where required, and rejected on invalid correlation.

Malformed, duplicated, replayed, out-of-order, oversized, stale, or cross-session messages MUST fail closed.

### TB-3 Voice → Cognition

Audio/transcript-derived content is input data, not authority.

Voice interpretation MUST NOT bypass application authentication, authorization, capability admission, or execution controls.

### TB-4 Cognition → RPII / PIAE

Cognitive output is untrusted reasoning.

The application MUST bind cognitive decisions to:

- authenticated principal
- application session
- voice session
- interaction/turn
- correlation identifier

### TB-5 Capability → Execution

Only the existing controlled path may reach execution:

Capability Request
→ Capability Gateway / Aegis
→ Execution Admission
→ Secure Executor

The frontend, voice subsystem, model, or application transport MUST NOT bypass this path.

### TB-6 Runtime → Persistence

Persistent state MUST preserve identity, sequencing, revision checks, idempotency, recovery, and audit semantics already established by the persistence layer.

## 6. Application Runtime Responsibilities

The Application Runtime owns composition and orchestration only.

Responsibilities:

- initialize dependencies
- construct application services
- establish authenticated application context
- establish/bind voice sessions
- establish interaction/turn context
- route validated input
- invoke existing cognitive/voice services
- route capability requests through existing boundaries
- expose results through approved application contracts
- manage cancellation/interruption
- manage reconnect/resume
- enforce application-level resource limits
- expose safe health/readiness information
- emit correlated observability events

The Application Runtime MUST NOT:

- implement a second authorization engine
- execute privileged operations directly
- store plaintext provider secrets in frontend-visible state
- trust model output as executable authority
- manufacture capability grants
- duplicate the persistent execution runner

## 9. Barge-in / Interruption

Barge-in MUST be first-class runtime behavior.

Requirements:

- new user speech can interrupt generated output
- cancellation is correlated with the active turn
- late provider output cannot resume cancelled playback
- stale events are rejected
- cancellation is idempotent
- interruption does not create a second unauthorized execution path
- recovered turns preserve session continuity
- partial audio/output state cannot corrupt subsequent turns
---

## 10. Realtime Contract

Transport responsibilities:

- WebSocket SHALL provide the application realtime control/event channel.
- WebRTC SHALL be the preferred browser media transport for realtime voice in the 19.4.11 target architecture. A non-WebRTC fallback MAY exist for compatibility, but MUST preserve the same Application Runtime and security boundaries.
- Transport choice MUST NOT weaken authentication, authorization, session binding, validation, auditing, or resource controls.

The initial protocol SHALL define:

```text
CLIENT → SERVER
- session_init
- audio_start
- audio_chunk
- audio_end
- text_input
- interrupt
- cancel
- ping
- resume

SERVER → CLIENT
- session_ack
- turn_started
- transcript_delta
- cognitive_state
- response_delta
- audio_start
- audio_chunk
- audio_end
- interrupted
- cancelled
- error
- degraded
- recovery
- session_resumed
```

Every event SHALL contain or be unambiguously bound to:

- protocol version
- event type
- unique event/request identifier
- authenticated principal context
- application session identifier
- voice session identifier where applicable
- interaction/turn context where applicable
- sequence information where ordering applies
- bounded payload

Unknown event types MUST fail safely.
Malformed event payloads MUST be rejected.
Replayed or stale events MUST be rejected.
Cross-session events MUST be rejected.

## 12. Authentication and Authorization Boundary

The application MUST distinguish the following stages:

```text
Authentication
    ↓
Principal Identity
    ↓
Application Session Binding
    ↓
Application Authorization
    ↓
Capability Authorization
    ↓
Execution Admission
    ↓
Secure Execution
```

Voice authentication remains an identity signal only.

A successful voice identity result MUST NOT by itself authorize privileged execution.

Frontend possession, browser state, WebSocket possession, transcript content, model output, or voice output MUST NOT be treated as proof of execution authority.

Authentication and authorization failures MUST fail closed.

## 13. Browser Security Boundary

The browser is an untrusted client environment.

The frontend MUST enforce or be deployed with appropriate controls for:

- secure context
- explicit microphone/media permission
- strict Origin validation
- Content Security Policy
- XSS protection
- safe input/output encoding
- CSRF protection where applicable
- secure credential/token handling
- no provider/API secret exposure
- safe local storage usage
- safe error rendering
- safe model-generated content rendering
- reconnect abuse protection

Frontend code MUST NOT contain privileged credentials.

Frontend-controlled state MUST NOT be trusted as an authorization source.

Microphone access MUST remain behind the browser media-permission boundary.
---

## 14. Audio / Privacy

Audio, transcripts, voice identity data, and related runtime metadata MAY contain sensitive information.

Privacy requirements:

- raw audio MUST NOT be written to ordinary application logs
- authentication material and secrets MUST NOT be logged
- transcript retention MUST be explicitly bounded
- audio retention MUST be explicitly bounded
- sensitive data MUST be minimized at every boundary
- diagnostic metadata MUST remain separable from sensitive payloads
- provider requests MUST contain only the minimum required context
- unrelated session data MUST NOT cross a provider boundary
- error responses MUST NOT expose sensitive internal state
- persistence of raw audio MUST require an explicit approved design

Privacy controls MUST apply to both normal and failure paths.

---

## 15. Resource and Backpressure Controls

All externally influenced resource consumption MUST be bounded.

The application SHALL define limits for at least:

- simultaneous application sessions
- simultaneous voice sessions
- active turns per session
- incoming HTTP body size
- realtime message size
- audio chunk size
- queued inbound audio
- queued outbound audio
- generated response buffering
- concurrent cognitive requests
- concurrent provider requests
- reconnect attempts
- resume attempts
- request execution duration
- idle session lifetime

When a limit is reached, the runtime MUST fail safely or apply controlled backpressure.

Untrusted clients MUST NOT be able to cause unbounded memory, CPU, network, provider, or database consumption.

---

## 16. Reconnect / Resume / Idempotency

Reconnect and resume behavior MUST be explicitly modeled.

Requirements:

- session identity is preserved only when the session remains valid
- expired sessions are rejected
- stale sessions are rejected
- session revision/sequence protection is preserved
- duplicate requests are handled idempotently where the operation permits it
- replayed realtime events are rejected
- stale realtime events are rejected
- partial operations are recoverable or safely terminated
- recovery MUST NOT repeat unauthorized execution
- recovery MUST NOT manufacture a new authorization decision

Existing persistence/session mechanisms SHALL be reused where they already satisfy the required semantics.

The application MUST NOT create a second incompatible session-continuity model.

## 19. Frontend / HUD-FUI Boundary

The frontend is an application client, not a privileged control plane.

Minimum frontend responsibilities:

- display connection/session state
- display microphone/listening state
- display processing/responding/speaking state
- display interruption/cancellation state
- display degraded/error/recovery state
- provide text input/output fallback
- provide accessible non-voice controls
- safely render approved cognitive responses
- expose no privileged backend credentials

The frontend MUST treat all server/model-generated content as untrusted content for rendering purposes.

HUD/FUI implementation MUST follow the existing LYRION visual source-of-truth rather than introducing an unrelated visual language.

Frontend state MUST NOT create, grant, infer, or elevate authorization.
